# Release driver

`tools/release_driver.py` runs the release stages declared in
`ops/mvp2-release/release-stages.json` (RELEASE-DRIVER-001). It replaces the
hand-written `chain_*` / `t_*` scripts that the R1 and R2 builds generated by string
substitution. The graph is data: the driver holds no tool names, and every id and path
in an argument is a placeholder resolved from the run configuration, a graph path or an
id the driver derives from the run's own outputs.

```
python tools/release_driver.py plan   --config run.json
python tools/release_driver.py plan   --config run.json --offline --ids ids.json --recorded cmds.json
python tools/release_driver.py run    --config run.json [--only STAGE | --through STAGE] [--replace]
python tools/release_driver.py check  --config run.json [--only STAGE | --through STAGE]
python tools/release_driver.py gate-commit --config run.json --confirm-release-id ID
python tools/release_driver.py status --config run.json
python tools/release_driver.py stop   --config run.json
```

Exit 0 succeeded, 1 a stage failed, 2 a refusal or usage error.

## Run configuration

`run.json` holds absolute paths and the frozen code identity: `repo_root`, `python`,
`cycle` (the scratch cycle directory that holds state, logs and production outputs),
`run` (the attended run's output root), `qa`, `code_commit`, `pipeline_id`,
`mode`, `live_workspace` (probe), `requested_as_of`, `history_store`, `expect_superseded`, `build_portfolio_root`,
`portfolio_root`, `retained_cache_root`, `resolved_cycle` (the `qe-release-resolved-cycle/1` file of the cycle manifest: the output path of stage `cycle-resolve`, read by the staging, `pre-chain` and `post-commit-verify` stages), and `provider_sources` (root id to the provider
generation directory the release binds, or the string `from_ledger`, below). The epoch manifest
generation comes from the run itself.

`provider_sources: "from_ledger"` derives the seven provider rows from the cycle manifest's roots, not a
typed map: each source is the `generation_dir` the resolved cycle (`{resolved_cycle}`, default
`{cycle}/resolved-cycle.json`, written by `release_cycle_manifest.py resolve --out`) carries for the provider,
`<root of the provider's manifest root key>/generations/<generation_id>`. `{cycle}/ledger-spec.json` (built by
`tools/release_ledger_spec.py` from the same manifest) must agree on root, generation id and manifest hash, so a
provider staged in one root and bound from another is refused instead of guessed. The stage also refuses when the
staged ledger catalog (graph path `ledger_catalog`) admitted another generation id for a provider, or when the
directory is not that generation inside its root (a link leaving the root counts). A provider whose bytes live in
another root is declared that way in the cycle manifest; the former config key `real_root_overrides` is retired
and any run configuration that still has it is refused. In this mode the stage records the ledger spec, the
resolved cycle and the ledger catalog as inputs (graph key `config_inputs`), so a kept stage is refused when one changed. See `docs/release-ledger-spec.md`. A test fails if the graph starts using a key this list does not name.

## Interpreter

Everything the release hashes into a pin, a seed or a generation id (the implementation reconciliation and return attribution
seeds, the sleeve-basis contract, the TuringTrader source manifest, the report and every later generation) is computed in floating
point, and CPython 3.12 made the built-in `sum()` of floats compensated: the same inputs give other last digits there (R3 pass 6e: an
attribution built on 3.13 differed from the 3.11 one in five fields, e.g. `0.9795932641808844` against `...839`). So **pin-feeding
builds run under the 3.11 venv only**; the tooling venv of the release-inputs work (3.13) must not build seeds or anything pinned.

`requires-python` admits 3.11 to 3.13 for development, `.python-version` only picks uv's default and CI proves the tests pass on 3.11:
none of them constrains the interpreter a run or an operator uses, so the guard is explicit
(`quant_engine.core.interpreter`, one required version, a refusal that names the interpreter found and the one required):

- the graph names it (`required_python`, `3.11`, required by the schema and part of every stage binding, so a kept receipt from another contract is not reused): before any stage that runs `{python}` the driver probes that interpreter once and
  refuses a stage on another (offline plans do not probe);
- the tools that compute numbers refuse on another interpreter at their entry point, exit 2: the implementation reconciliation, the
  implementation return attribution, the implementation sleeve basis, the TuringTrader source manifest builder (every command: `build`, `verify`, `read-compat`)
  the release builder (`build` and `stage`: `recipe` and `inventory` only hash files), and every other pipeline tool that does float
  arithmetic, on every subcommand: attribution, correlation, decomposition, diligence rubric, driver map, Grizzly signal replay, replication,
  report, strategy history, target series, control panel and provider ledger (`tests/core/test_interpreter_guard.py` lists each
  subcommand and fails for a new tool that computes figures and is neither guarded nor excused with a reason);
- the attended run records the interpreter it probes (`_runtime_identity`) and refuses one that is not 3.11.

No guard is needed in the tools that only hash, copy or compare files and never compute a figure: `release_inputs.py` (including
`rebind-predecessor`), `release_cycle_seeds`, `release_prepare_inputs`, the baseline, ledger and provenance spec builders,
`release_hwm_calendar` and `release_fresh_world`.

## Probe and release mode

`mode` is required and is `probe` or `release`. A probe runs on a scratch copy of the real
roots: with `live_workspace` set to the real `_quant_engine` directory, every stage from the
production spec onward refuses (exit 2) when the spec's coordination root, state root or any
root, or the `portfolio_root` argument, lies inside it. `release` mode does not guard and is
used only for the attended release itself.

## What a stage may start on

A stage is refused (exit 2, nothing changed) unless

- the repository is at `code_commit` with a clean tree (checked again after the stage; a
  stage that moved or dirtied the repository fails);
- every stage it requires finished at that code identity and its recorded outputs still hash
  to what was recorded, so a leftover from another pass is never read as an input;
- none of its create-only outputs already exists. `--replace` renames a colliding output to
  `<name>.prev-<timestamp>` instead of deleting it;
- every `assert_equal` pair of derived ids agrees: the findings stage compares the panel
  generation the run produced with the one the production spec binds, so it cannot run
  against another generation;
- every derived id resolves to exactly one entry (one ledger generation, one epoch
  generation).

A stage's result is its tool's exit code. The driver never reads a log to decide pass or
fail. `checks` assert fields of a JSON output (the plan must be ready with no blocking
reasons). A stage that must not move a pointer (the dry run) snapshots every pointer the
release can move before and after; only the release directory the stage reports as its own
may appear.

`provider-generations` is generated from the configuration and the run, never written by
hand, and refuses when a bound root has no source, a source is missing, or the configuration
names a root the graph does not bind.

## Commit gate

A stage that declares `commit_gate` (the `execute --commit` stage) refuses unless

- `mode` is `release` and `--confirm-release-id` equals the release id the dry run reported:
  the exact release the owner confirmed, not a hash the driver chose;
- every named replica stage (commit, post-release verify, rehearsal, restore) finished `ok`
  at the run's code identity;
- the replica spec and the real spec have the same topology (`spec_topology`: node ids,
  dependencies, generation ids and manifest hashes, artifact hashes, companions, code
  commit, as-of date, pipeline id; paths and roots are left out because they legitimately
  differ), and the real spec binds the run's code commit;
- the declared inputs (provider generations, financial artifacts) are byte-identical between
  the real run and the replica;
- the release is prepared on disk, and no pointer has moved since the dry run snapshot.

The graph adds the commit stage together with the replica ceremony stages it names.

## Restoring the replay world

`tools/release_restore_world.py` rebuilds the input world a replay needs (the old worktree and
scratch paths a prior release's specs name) from the OneDrive evidence archives declared in
`ops/mvp2-release/replay-world.json`. It reads every absolute path and `{path, sha256}` pin in the
given specs, restores what falls under an old root into `--dest`, verifies each restored file
against its pin, and writes a resolution report. Exit 1 on a hash mismatch or on a missing path not
named by `--allow-missing` (inputs the cycle regenerates). Run on the R1 release spec it restores 17
pinned inputs and names the one it cannot find. It writes only `--dest` and `--report`.

## Packing evidence

`tools/release_evidence_pack.py` copies the cycle's state, logs and stage outputs (the
`pack-evidence` stage, an explicit stage like the commit) into `evidence_dest`, a OneDrive evidence
directory, with `SHA256SUMS.txt` and a `manifest.json` (file count, code commits, stage statuses).
It is create-only: an existing file with other bytes is a refusal, `--dest` may not be inside the
cycle, and a link out of the cycle is refused. The packed directory is re-hashed against its sums
before the tool reports success.

## State

`<cycle>/release-driver-state.json` records per stage its status, code identity, seconds,
exit code, log path, output digests and, when the stage writes them, `work_counters`. Logs are
`<cycle>/logs/<stage>.<attempt>.log`, one per attempt, so nothing greps a stale file name.

## Stage graph and schema

`ops/mvp2-release/release-stages.json` is validated on load against
`ops/mvp2-release/release-stages.schema.json` (unknown keys, a missing `argv`, a repeated id or a
`requires` that does not precede its stage are refused before any stage starts). Stage order:

| group | stages |
|---|---|
| staging | `cycle-seeds`, `cycle-resolve`, `provenance-spec`, `provenance`, `ledger-spec`, `ledger`, `implementation-reconciliation`, `implementation-return-attribution`, `baseline-spec`, `baseline` (below, "Staging group") |
| inputs | `selected-build` (`release_prepare_inputs.py selected`), then `selected-inputs` (the selected-inputs file and the hand-built attribution spec must exist and are hash-bound; the file must name this run's ledger generation) |
| pre-chain | `pre-chain` (`tools/release_pre_chain.py`: layered history, dependence, attribution; reads the resolved cycle) |
| calendar | `calendar-authority` (explicit: authors the HWM calendar authority from a first attempt; below) |
| preparation | `prep-spec` (`release_prepare_inputs.py prep-spec`: the attended preparation spec; pins the calendar authority) |
| attended | `attended` (QA hold), `qa-browser`, `qa-interaction`, `qa-native`, `resume` |
| tail | `recipe-probe`, `registries`, `recipe`, `pipeline-spec`, `semantic`, `financial-artifacts`, `provider-generations`, `production-spec` |
| replica ceremony | `replica-copy`, `replica-provider-generations`, `replica-spec`, `lanes` (real lane: preflight, plan, dry-run, findings; replica lane: preflight, dry-run, findings, commit, post-release verify, rehearsal, clean-room restore) |
| release | `pack-probe` or `commit` then `pack-evidence` (explicit) |

`preflight`, `plan`, `dry-run`, `findings-panel` and `findings-targets` remain as explicit
single-stage diagnostics of the serial path (pass 21); the release path is `lanes` (pass 26).
The attended preparation spec (`mk_prep_spec.py`) is a per-cycle input builder, not a stage: the
driver refuses it unless it names this run's history, attribution, baseline and ledger
generations (`bound_ids`).

The graph starts with the committed replacements of the R2 staging hand scripts (`stage_p23.sh`: provenance,

what it wrote; everything is written under `{cycle}` and in both ceremonies (no `only_ceremony`: nothing here
touches a real root).

|---|---|---|---|
| `cycle-resolve` | `release_cycle_manifest.py resolve` | `{resolved_cycle}` | the manifest bytes differ from `cycle_manifest_sha256`; any pin, hash, generation or finality rule of the manifest fails; the resolved cutoff or evaluation date is not the run's `requested_as_of` / `evaluated_on` |
| `provenance-spec` | `release_provenance_spec.py refresh` | `{cycle}/provenance-spec.json` | the seed `provenance_spec` differs from `provenance_spec_sha256`; a contract, registry or schema named by the seed has no file in the repository |
| `provenance` | `portfolio_provenance.py stage` | `{cycle}/prov` | the derived spec differs from what `provenance-spec` recorded |
| `ledger-spec` | `release_ledger_spec.py build` | `{cycle}/ledger-spec.json`, `{cycle}/run-observation.json` | the predecessor spec differs from its pin; the builder's own self-check (the committed ledger validator) fails; the spec's cutoff or provenance generation is not this run's |
| `ledger` | `provider_ledger.py stage` | `{cycle}/ledger` | the spec does not name this run's provenance generation (`bound_ids`); the stage passes `--output-root` itself so a spec cannot send it elsewhere |
| `baseline-spec` | `release_baseline_spec.py build` | `{cycle}/baseline-spec.json` | release inputs missing, of another cutoff or not matching their pin; the spec's cutoff, ledger or provenance generation is not this run's |

### Selected inputs and preparation spec (block B4)

`selected-build` writes `{selected_inputs}` (create-only) from a predecessor selected-inputs file: the contract, the
three provider-ledger paths of this cycle's ledger generation and `repository_sha` (the run's `code_commit`, passed with
`--commit`; the tool never reads git) are rebound, every other entry is carried only after its bytes match the predecessor's
pin. `selected-inputs` then checks the file exists and, by `bound_ids`, that it names this run's ledger generation. (The file
carries no baseline generation id, so none can be checked there; the baseline is bound by the preparation spec below.)
`prep-spec` runs after `pre-chain` (it needs the history and attribution generations) and writes `{preparation_spec}`
(create-only); the committed attended planning path validates it before the stage ends. `attended` requires it and keeps its
own `bound_ids`. The calendar authority comes first in the order: `prep-spec` binds `{calendar_authority}` and refuses any
file other than the one pinned by `calendar_authority_sha256`; the seed authority for a first attempt is an operator file
(no committed tool writes it), the second attempt's is the `calendar-authority` stage's output (`--replace` moves the seed
aside).

| key | meaning |
|---|---|
| `predecessor_selected_inputs`, `predecessor_selected_inputs_sha256` | the predecessor's selected-inputs file and its pin |
| `predecessor_prep_spec`, `predecessor_prep_spec_sha256` | the predecessor's attended preparation spec and its pin |
| `rebind_cutoff` | optional, `"true"`: pass `--rebind-cutoff` to both builders (a predecessor of another cutoff) |
| `selected_files` | optional object `NAME: "ROOT_KEY:relative@sha256"`: one `--file` per entry (the new native file of a carried entry) |
| `factors_bundle`, `sector_bundle`, `style_bundle` | optional public bundle names (`--<kind>-bundle`); the default is the bundle roots the resolved cycle names |
| `factors_bundle_id`, `sector_bundle_id`, `style_bundle_id` | optional: choose one generation of a bundle root that holds two (`--<kind>-bundle-id`) |
| `implementation_model_book_perf` | optional `"ROOT_KEY:relative@sha256"` (the model book performance export of the declared sleeve, passed as `--pin`). A run that names a `release_inputs_root` needs no key: when the inputs hold `model-book-perf.csv` under `ops/mvp2-release/inputs/implementation/`, prep-spec pins it itself (root key `release_inputs`, which the preparer binds to `--release-inputs-root`), unless this key is set. A run that hand-pins `implementation_sleeve_basis` through `prep_pins` must use inputs without the export (the two are refused together). Present, the attended preparation builds the `implementation-sleeve-basis/1` contract itself in a checkpointed stage after `sleeve-facts` (declaration, facts, this export, the retained attribution and reconciliation, the ledger's admission receipt); absent, an optional pinned `implementation_sleeve_basis` is used as before. Naming both is refused |
| `weekly_gap_fill_spec`, `vendor_gap_fills`, `model_vs_actual_input` | optional per-cycle inputs, each `"ROOT_KEY:relative@sha256"`, passed as `--pin KEY=...`; absent means the key is omitted from the spec |
| `prep_pin_root_key`, `prep_pin_root` | optional: a root key of the resolved cycle (such as `world`) and the directory it names. Present, `prep-spec` re-pins `implementation_reconciliation` and `implementation_return_attribution` from `{cycle}/in/implementation-*.json` (`--pin KEY=ROOT_KEY:relative@sha256`, the digest and the path relative to `prep_pin_root` derived from the files the cycle holds), so a cycle whose seeds differ from the predecessor's no longer refuses with `HASH_MISMATCH`. Absent, the command line is unchanged |
| `prep_pins`, `prep_dirs` | optional objects `KEY: "ROOT_KEY:relative@sha256"` / `KEY: "ROOT_KEY:relative"`: `--pin` / `--dir` replacements of carried inputs. A directory-valued field (such as `sleeve_facts.quantbase_source_dir`) belongs in `prep_dirs`: a pin writes a `{path, sha256, size_bytes}` object where the attended preparation reads a path |
| `prep_omit` | optional list of spec keys the cycle declares it has none of (`--omit`) |

The graph's `config_paths` require the file-valued keys above to exist before any stage runs.

A release that declares a strategy basis (`strategy-basis-declaration`, pinned by the sleeve policy manifest) needs the attribution catalog to carry the `strategy_basis` block and the sleeve comparison lanes, or the report refuses it ("attribution sleeve comparisons differ from the report's strategy basis restatement"). `pre-chain` stages the cycle attribution before the sleeve facts exist, so the attended preparation stages it once more, after the sleeve facts, the basis history and its dependence, from the same `attribution_spec_template` and baseline (`preparation/attribution`); the recipe then names that generation, as it already does for the rebuilt history. The attribution id the preparation spec carries (and `attended` binds) stays the `pre-chain` one; it is not the id the recipe uses when a basis is declared. A release without a declaration is unchanged.

Two driver features serve these stages and are part of the graph schema: an argv group `{"for_each": KEY, "args": [...]}`
repeats its arguments for every entry of the run-config object (or list) KEY (`{each_key}`, `{each_value}` stand for the entry),
and the derive rule `{"file_sha256": PATH}` yields the digest of a file an earlier stage wrote (the resolved-cycle pin
the calendar tool authenticates its input with). Under `plan --offline` a configured `release_inputs_root` that cannot be
opened because the directory is absent (not mounted) is not an error: the plan shows the baseline path in that root and binds no bytes.

### Calendar authority (explicit stage)

`calendar-seed` (explicit, requires only `cycle-resolve`) runs `release_hwm_calendar.py reissue` and writes
`{calendar_seed_reissued}` (`{cycle}/calendar-seed-authority.json`): the predecessor authority (`calendar_seed_authority`, pinned) with
`hwm_policy_sha256` rebound to the frozen repository's HWM policy and `authority_evidence_sha256` recomputed, every calendar, interval and
value carried. The attended run validates the authority it is given against the repository's policy before it stages anything, so a seed
carried from another head (the R3 rehearsal: `a01a9500` against `a6b85d7b`) is refused; the first attempt takes this file as its
`calendar_authority`. `calendar-authority` itself derives the policy hash from the repository and takes only the policy id and the owner
decision text from its seed, so it works on the same head with the original or the re-issued seed.

`calendar-authority` runs `release_hwm_calendar.py author` (two passes: calendar kinds and gaps from the first
attempt's observed NAV dates, then the adapter's own interval returns) and writes `{calendar_authority}` and
`{calendar_authority}.receipt.json`. It is explicit and nothing requires it: it needs a first attempt's staged run
(`calendar_attempt_run`, a run directory other than this cycle's `run`), which a default run cannot have. Order of
use: run the first attempt, `run --only calendar-authority`, set `calendar_authority_sha256` to the file's sha256
(`prep-spec` and `attended` then refuse any other file, the carried-over authority included), and `rerecord --confirm-same-config`
the completed stages. `release_hwm_calendar.py author --check` re-derives and refuses a differing file.

The graph schema still accepts `pinned_script` for an operator script outside the repository; the shipped graph uses
none (`pre-chain` runs the committed `release_pre_chain.py`).

Not in the graph (no committed tool covers it, or it needs inputs a stage cannot yet name): the provenance spec
builder, the IBKR generation staging (`ibkr_generation.py`; pass 26 reused the real-root generation), the
the public bundle and Quantbase source assemblers
(`release_public_bundles.py`, `release_quantbase_sources.py`, block B7; they write under the bundle roots the manifest
names, which lie outside the cycle) and the acceptance-input manifests (B9).

## Refusals seeded from R2's incidents

`tests/portfolio_operations/test_release_driver_stages.py` fires each refusal on a seeded input:

- a script path that points at another repository (the probe clone): a stage script must be a
  file inside `repo_root`;
- a stale cache base after a root rewrite: `config_paths` requires `retained_cache_base` to exist
  and every cycle path to lie inside the cycle;
- a HEAD assertion that no longer holds: the repository must be at `code_commit`, clean, before
  and after each stage; `check` reports it without running anything;
- findings against the wrong generation: `assert_equal` of the run's panel generation and the
  spec's; a preparation spec naming another pass's generations: `bound_ids`;
- grepped log names: the driver reads exit codes and JSON fields, never a log.

## Resume, PIDs, timing

A stage whose process was killed is recorded `running` with the PID and start token the driver
launched; the next `run` marks it `interrupted` when that process is gone (a live one blocks the
run) and restarts only that stage: `resume.same_argv` reruns the same command over its partial
output (the tool checkpoints itself, as `release_pre_chain.py` and the attended `--resume` do);
`resume.argv` runs a different command; a stage without `resume` has its outputs moved aside and
reruns alone. Completed stages are verified, not rerun. `stop` (and Ctrl-C) kills the process tree
of recorded PIDs only, and only while the recorded start token still matches, so a reused PID is
never touched. Every stage records `seconds`, `seconds_total` over its attempts, `attempt`, and
`work_counters` (from the stage's `counters` JSON or the `counter_keys` found in its output).
`<cycle>/release-driver-timing.log` has one line per start and finish.

## Offline plan

`plan --offline --ids ids.json --recorded cmds.json` prints every stage's command line from the
configuration and graph alone (derived ids come from `ids.json`; nothing under the run is read)
and compares each recorded command flag by flag. `tests/portfolio_operations/pass26_commands.py` builds the pass-26
configuration, its ids and its recorded command lines; the plan reproduces all 19 recorded stages (the 16 of
pass 26 and the three staging tools of `stage_p23.sh`; the spec builders, `selected-build` and `prep-spec` replace
hand scripts whose command lines are not tool calls and get no entry). A difference with a stated reason is listed under `known`: the ledger stage's explicit `--output-root`, and
the baseline path of `lanes` (R3 reads it from the pinned release inputs).

## Commit gate and the replica receipt

`commit_gate.replica_verify` runs `tools/release_replica.py verify` on the receipt. The receipt is
written only by the `lanes` ceremony and names all seven steps (preflight, dry-run, findings,
COMMIT, post-release verify, recovery rehearsal, clean-room restore, each rc 0) for the real
spec's topology and code commit; the driver's gate adds the confirmed release id, the topology of
the replica spec, a prepared release and unmoved pointers.

## Refusals before staging and before the attended run

Inputs that left Git with the release-inputs cutover are named by the stages that read them (`release_inputs`
in the graph): `baseline-spec` needs the baseline declared-inputs file, `prep-spec` the epoch crosswalk, the
sleeve policy manifest and the sleeve inputs (sleeve declared inputs, nested strategy tag map, disclosure inputs,
timestamp delta result, Quantbase declared inputs). A pinned set that lacks one refuses at that stage before it
runs, naming the file. `prep-spec` reads the crosswalk and policy through that set
(`--release-inputs-root`, `--release-inputs-manifest-sha256`). The cycle manifest's `public_bundles` name the
bundle roots (the directories that hold the generations), never a generation directory. The disclosure inputs'
`predecessor_comparison` is checked against the COMMITTED `CURRENT_RELEASE.json` and panel (below), so once
a release commits, the next cycle needs a release-inputs root whose comparison names it; a pin still naming the release before
refuses at `selected-inputs`. `tools/release_inputs.py rebind-predecessor --root <root> --manifest-sha256 <pin> --data-root <workspace>
--out <new root>` builds that root: the release id, panel generation and dashboard data file (id and sha256) are derived from the
committed release in the workspace, never typed; only the authored `pointers` are kept, the sleeve policy manifest's pin of the
disclosure inputs and the root's manifest are rebuilt, and the new manifest sha256 (the pin the run configuration takes) is printed.
It refuses a non-empty target, a release that is not committed, a disclosure file in another format, and any other file in the root
that still names the old release or panel (`--allow-stale-references` lists them and goes on). A root that already names the committed
release is reported `already_current` and nothing is written. The predecessor set files (`predecessor_selected_inputs`,
`predecessor_prep_spec`, `predecessor_ledger_spec`) are a separate input: the previous cycle's own seeds, not compared with `CURRENT_RELEASE`.

Three stale inputs each cost R2 hours; the driver refuses them at the first stage that could use them:

- **Predecessor vs CURRENT_RELEASE** (`selected-inputs`, `predecessor_check`): the disclosure inputs'
  `predecessor_comparison.release_id` must equal the COMMITTED `CURRENT_RELEASE.json` release id,
  `panel_generation_id` the panel `CURRENT.json` generation, and the pinned data file must hash to its pin.
- **Expected baseline** (`selected-inputs`, `expected_baseline`, `pinned_inputs`): its `cutoff` must equal
  `requested_as_of` and its bytes the run's `expected_baseline_sha256`. The baseline file records no ledger
  or Schwab generation id, so the sha256 pin (set when the baseline is derived for this ledger) is what binds it
  to the run's inputs; the full invariant check remains the validator at the findings step.
- **Calendar authority** (`attended`, `pinned_inputs`): `calendar_authority` must hash to the run's
  `calendar_authority_sha256`, so the previous pass's authority is refused before the 9-minute attended start.
  The authority itself is re-authored from the first attempt's staged evidence with
  `tools/release_hwm_calendar.py author --resolved-cycle <resolved.json> --resolved-cycle-sha256 <pin> --run <first-attempt run dir> --spec <spec.json>
  --seed-authority <predecessor authority> --out <authority.json>` (two passes; create-only, with a receipt beside it;
  `--check` re-derives and refuses a differing file), then its sha256 is pinned in the run config. The driver does not
  derive it: that needs the epoch stage's output and the adapter internals. The policy id and owner decision text are
  carried from the predecessor authority; every interval value is one the adapter derived.

## Ceremony: real roots or replica only

The run config must declare `ceremony`; a run without it is refused, so writing the real roots is never a default.

- `full`: the release path (`attest`, `lanes`, `commit`, `pack-evidence` write or prepare on the real roots).
- `replica-only`: a rehearsal. The real-root stages are refused (`only_ceremony: full`) and the replica stages run instead:
  `replica-copy`, `replica-attest` (the attestation goes to the replica coordination root, derived from the real layout),
  `replica-spec`, `ceremony` (`release_replica.py ceremony`; the receipt is at the path the commit gate reads).
  Every stage's declared outputs, snapshots and updated paths are refused when they lie inside a root registered as real
  (`source_workspace`, `live_workspace`, `coordination_root`, plus any `real_roots` in the config), and the `ceremony`
  stage refuses a replica spec whose coordination, state or release roots are real or outside the replica workspace.
  Both modes run the same code: the config value only selects which stages apply and which guard is active.

`check`, `run` and `plan --offline` print which ceremony they are in. Switching the ceremony keeps completed stages (it is
left out of the run binding); any other configuration change invalidates them.

## Post-commit verification (real roots)

Stage `post-commit-verify` (release mode, full ceremony, requires `commit`; `pack-evidence`
requires it) runs `tools/release_post_commit.py verify`. It replaces the hand-run
`t_post_real.sh` and the post-commit half of `t_commit_real.sh`:

1. the commit result is `COMMITTED` for exactly this spec; `CURRENT_RELEASE` names the committed
   release, which is not the cycle's predecessor; the predecessor's release directory is still
   present; the only release directory added is the committed one; `CURRENT_RELEASE` moved;
2. `portfolio_qc.py --profile post-release-verify` exits 0 and its receipt is PASS for this spec,
   release and the single preflight receipt, with its authority digest equal to the
   `CURRENT_RELEASE` pointer;
3. `data_recovery_rehearsal.py` and `verify_release_restore.py` exit 0 against the same real spec,
   each into a fresh root under `post-commit/`.

The repository must be clean at `code_commit` before and after. The post-commit pointer snapshot
(`post-commit-pointers.json`) and a create-only receipt `post-commit-verify.json`
(`qe-post-commit-verify/1`: file digests and ids, no absolute paths) are written under
`{cycle}/post-commit/`.

The single preflight receipt is the real lane's (`{lane_real}/evidence`, the dry run the commit authorization came from).
After the commit the stages before it are re-verified for their recorded bytes but no longer against the predecessor pin:
the pin names the release the run replaced and `CURRENT_RELEASE` is now the run's own, so a pin check would refuse every
post-commit stage by construction. The pin was checked, when it was true, by the stages that carry the rule.


Neither implementation stage takes the desktop workbook: it is on permanent hold (AGENTS.md), so the shipped graph passes no
`--tt-workbook` and lists no `tt-workbook.xlsx` among the stages' release inputs. The reconciliation never needed it (its
workbook is an optional diagnostic); the return attribution takes the six TuringTrader components and their weights from the
governed source manifest (owner ruling 2026-10-10, constant mix since inception) when no workbook is given. A release-inputs
set that holds no workbook is therefore complete. Both stages record the P123 and IBKR generation directories and the Schwab
catalog they read as inputs, so a change in place after the stage ran fails the resume check instead of passing it.


### Findings inputs

Only when the run names a `release_inputs_root` (one optional argument group); a run without one keeps the repository-default command lines.

The findings step of `findings-panel`, `lanes` and `ceremony` runs `validate_generation.py` with the inputs the attended
run used, so a sleeve row is checked against the declaration it was restated from (#624): `--strategy-basis` and
`--tag-map` (release-inputs-root files `sleeves/strategy-basis-declaration.json` and `sleeves/nested-strategy-tag-map.json`),
`--sleeve-facts` (the run's `stages/report` generation input), `--provider-ledger` (the run's ledger catalog) and
`--ibkr-root` (the preparation spec's `sleeve_facts.ibkr_generation_root`). `release_replica.py` takes the same five as
optional flags and adds them to the validator only when given. Without them the declaration-dependent items
(`returns.sleeve_basis` and its invariants) are not evaluated and the ceremony reports different findings than the run.

## Re-running a pass on a fresh world

Cold-operator checklist (R3), with the numbered recipe below as the detail: (a) the release-inputs root and its manifest
pin (`release_inputs.py verify --root <ri> --manifest-sha256 <pin> --cutoff <date>` passes); (b) the predecessor set (the R2.2
`selected-inputs.json`, preparation spec and ledger spec) with their pins, remapped by step 5 from the world they were produced in
(`C:\Dev\scratch\qe-p32`), and the seed authority file and its trust pin the owner gave; (c) the 3.11 venv for every command
below (the tools and the driver refuse another interpreter); (d) a frozen clone at the candidate commit; (e) steps 1 to 5
(seed, `config`, `move-aside`, `carry-over`, remap), then step 6 (`cycle-seeds`, `cycle-resolve`, `calendar-seed`), then
step 7 (`run`, the ceremony); then the replica verification and the owner's direct hash confirmation. Every step is a committed
tool; none needs a hand-written script.

Three steps of a re-run are operator steps by design, not graph gaps:

- `calendar_seed_authority_sha256` is a trust pin the operator supplies (`sha256sum` of the seed file the owner pinned); the
  stages refuse any other bytes, so the graph does not compute it from the file it checks. `calendar-seed` is explicit: name it
  (`run --only calendar-seed`) after `cycle-resolve`, then point `calendar_authority` at `{calendar_seed_reissued}`.
- `replica-copy` is create-only (`must_not_exist {replica_workspace}`). A second pass over the same `replica_workspace` is refused
  by design; give each pass its own `replica_workspace` or move the earlier replica aside first (retire it after archiving).
- `implementation_model_book_perf` needs no key when the run names a `release_inputs_root` holding the export (see the run
  configuration table): without the export the attended preparation builds no sleeve-basis contract and the published
  implementation row stays on the account basis (finding `returns.implementation_account_legs`, N66).

Order of a fresh-world pass, with `tools/release_fresh_world.py` (create-only or idempotent, never deleting; `move-aside` and
`carry-over` print what they would do unless `--apply` is given). **Every command of the pass that builds a pin-feeding number (the stages, the seed builders, the attended run) runs under the 3.11 venv only** (see "Interpreter" above): the release-inputs tooling venv (3.13) must not run them, and the tools and the driver refuse another interpreter:

1. `provenance-seed --seed <previous seed> --release-inputs-root <ri> --release-inputs-manifest-sha256 <pin> --out <new seed>`: the seed's `sleeve-policy` root now
   names this pass's inputs and its source group's hashes are re-read from them. The printed sha256 is the new
   `provenance_spec_sha256`.
2. `config --previous <previous run json> --out <run json> --candidate-commit C --code-commit T --release-inputs-root <ri> --release-inputs-manifest-sha256 <pin>
   --set provenance_spec=<new seed> --set prep_pin_root_key=world --set prep_pin_root=<world> [--set run=... --set qa=...
   --set evidence_dest=...]`: repoints every occurrence of the old inputs root, verifies the inputs against the pin (never by repo path), takes the expected
   baseline pin from the verified set and recomputes the provenance seed pin from its file, derives the calendar authority's pin from the pinned seed (a pin of the previous pass is never carried) and drops `calendar_attempt_run` / `calendar_attempt_spec` when they point into a removed world (only the explicit `calendar-authority` stage reads them; it declares `needs_config` and refuses, naming the keys, when it is selected without them). Predecessor
   pins are never touched.
3. First stop every driver or stage process of the previous pass: a live child holds files in the world and the move fails
   with "Permission denied". Then `move-aside --config <run json> [--keep-cache] [--apply]`: the whole previous cycle directory (`prov`, `ledger`,
   `baseline`, `production`, the stage receipts and the rest: every stage records the run configuration it was produced under, so
   a leftover output refuses the next pass) and the configured `run`, `qa`, `evidence_dest` and `replica_workspace` that lie
   outside it get an `.aside-<UTC time>` name; nothing is deleted. `--keep-cache` moves the retained cache (`retained_cache_root`,
   inside the cycle) from the aside directory back into the fresh cycle, so a cache worth reusing is not rebuilt; a cycle that
   holds only that cache is already fresh and a second run moves nothing. A configuration-bound input inside the cycle (`provenance_spec`, `release_inputs_root`, `cycle_manifest`, `cycle_roots_file`, `calendar_seed_authority`, the `predecessor_*` files, `expected_baseline`, `disclosure_inputs`) is refused by `config` and by `move-aside` before anything is written or moved, because it would go aside with the old outputs: keep the fresh seed and the release inputs outside the cycle (a sibling of it, as `cyc/` is). A configured `run`/`qa`/`evidence_dest`/`replica_workspace` that is or contains the cycle, and two cycles that are or lie inside one another (`carry-over`), are refused too. Only paths inside the world are moved; an existing aside
   name is refused; the output lists each move (and the cache restore) with the aside name `carry-over` reads from.
4. `carry-over --from-cycle <the aside cycle> --to-cycle <cycle> [--carry RELATIVE ...] [--apply]`:
   `in/epoch-admission-policy.json` and each further file or directory named with `--carry` (the IBKR generation directory
   `ibkr/`, when the carried preparation spec still names it). The retained cache is not copied (see `--keep-cache`).
5. If the previous pass's `selected-inputs.json` and preparation spec (the predecessor set) still name its world, remap them with
   the same command as the ledger spec: `release_spec_remap.py remap --manifest <cycle manifest> --roots-file <roots> --mapping <map>
   --spec <original file> --out <remapped file> --expect-rewritten <N>`, the mapping naming the WHOLE old world prefix
   (`old_prefix`, `root_key`). It is create-only and fail-closed (a foreign absolute path or a missing carried target is refused) and
   `--expect-rewritten` refuses a mapping that matched another number of paths than the previous pass (42 in the R2.2 selected
   inputs, 44 in its preparation spec). The output is serialized canonically, so the `predecessor_*_sha256` pins are taken from
   the tool's output (`sha256` in its summary), not from the original file. Those pins and files go on `config` (step 2) as
   `--set predecessor_ledger_spec=<file> --set predecessor_ledger_spec_sha256=<pin> --set predecessor_selected_inputs=<file>
   --set predecessor_selected_inputs_sha256=<pin> --set predecessor_prep_spec=<file> --set predecessor_prep_spec_sha256=<pin>`.
   The remapped files must lie outside the cycle (`config` refuses them inside it), so step 5 can run before step 2; when a
   configuration exists already, run step 2 again with `--previous <that configuration>` and a new `--out`.

   The mapping file is plain data, written with any editor; no script is needed (the full schema and refusals are in
   `docs/release-spec-remap.md`). `old_prefix` is the world the predecessor files were produced in, and `root_key` the
   cycle root that world becomes. For R3 the predecessors are the R2.2 set, produced in `C:\Dev\scratch\qe-p32`:

   ```json
   {"schema_version": "qe-release-spec-remap/1",
    "mappings": [{"old_prefix": "C:\\Dev\\scratch\\qe-p32", "root_key": "world"}]}
   ```
6. The pre stages, now that the cycle is fresh (`move-aside` and `carry-over` have run, because these stages write into the
   cycle). `--only` runs exactly the named stage and checks that the stages it requires are done and unchanged; it does not
   run them, so the order is fixed (`calendar-seed` is `explicit` and never part of a full `run`):

   ```text
   release_driver.py run --config <run json> --only cycle-seeds
   release_driver.py run --config <run json> --only cycle-resolve
   release_driver.py run --config <run json> --only calendar-seed
   ```

   Without the third, the full run refuses (`calendar_authority` is missing). Nothing needs rerunning after `config`: the
   calendar authority's pin is already in the configuration (see below), so these stages keep the binding they were run under.
   `config --require-calendar` afterwards is an optional check that the pin is written; it produces an identical file.
7. `run` (full), in the foreground, or in the background with a log (the ceremony takes about an hour):
   `( release_driver.py run --config <run json>; echo "DRV_RC=$?" ) > <log> 2>&1 &` (POSIX shell; `nohup` only if the
   session may end). The log is the driver's own output, so watch it for `refused` / `failed` lines; `DRV_RC=0` ends it.

The calendar authority's pin is a deliberate trust pin, now derived rather than typed: `config` takes the seed the previous
committed release pinned (`calendar_seed_authority` with its `calendar_seed_authority_sha256`; any other bytes refuse), runs the
deterministic reissue against the frozen repository's HWM policy (`repo_root`) and writes the sha256 of the result as
`calendar_authority_sha256` (only when `calendar_authority` is the file the `calendar-seed` stage writes, `{cycle}/calendar-seed-authority.json`; any other authority, such as a later `calendar-authority` attempt, is pinned from its own file once it exists and stays pending until then), so one configuration write carries every pin before any stage runs. The `calendar-seed` stage
declares that pin and checks its output against it (`sha256_of`): a stage that writes any other bytes fails. A pin left in the
previous pass's configuration is never carried (it is dropped and re-derived), and a seed that is not the pinned file is refused.
The operator records the pin the command prints (`calendar_authority_sha256`) in the pass evidence, where the release owner's
direct hash confirmation at commit covers it. Without the seed keys there is no pin, and the `calendar-seed` stage refuses (it needs `calendar_authority_sha256`);
`config --require-calendar` still writes the pin from an existing authority file for the later `calendar-authority` attempts.
